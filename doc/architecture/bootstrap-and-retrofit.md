# Bootstrap & retrofit pipeline

All template rendering flows through a single code path: `bootstrap-cdd-project.sh`. Nothing else reimplements placeholder substitution.

(The third CDD-repo-only command, `/cdd-quick-create`, is deliberately *not* part of this pipeline: it produces a one-off deliverable by writing plain files directly, with no `template/`, no substitution, and no scaffold commit, so it never touches the bootstrap script. It is documented with its siblings in the [overview](overview.md) and the [feature doc](../features/template.md).)

Like `demo/setup.sh`, `/cdd-retrofit` does not duplicate substitution logic: its install mode drives `bootstrap-cdd-project.sh --stage`, a render-only mode (no `git init`, no scaffold commit) that stages a fully substituted template tree which the command then merges into the target interactively. Its upgrade mode additionally uses `--template-dir` to render an old template snapshot through the same single code path.

`/cdd-bootstrap` (greenfield) also routes through the script, but via the `demo/setup.sh` path rather than the retrofit path: it writes the guided-discovery artifacts (project overview, filled `CLAUDE.md`, resolved engineering-practices contract, real roadmap) into a staging overlay and runs `bootstrap-cdd-project.sh --overlay` once, in normal mode. The overlay overrides the template stubs before substitution, so `git init` + the scaffold commit capture the filled-in docs — no `--stage`, no post-hoc copying.

**Capability bindings flow through the same path.** The script's opt-in `--tracker`, `--code-host`, `--jira-site`, `--jira-key`, `--gitlab-project` and `--gitlab-url` flags write each bound capability's `.cdd/<capability>` shim after substitution and before the baseline marker, so a normal bootstrap commits them in the scaffold commit and a `--stage` render carries them for retrofit to copy under per-file approval. The division of labour is fixed: the prompts decide *which* backends (`/cdd-bootstrap` asks; `/cdd-retrofit` detects from the target's origin host — deriving GitLab's coordinates from the remote — and Jira-key-shaped refs, and proposes), and the script is the only thing that writes a shim. Upgrade mode passes the flags to its current render only, never to the old snapshot render. Shim shape, the adapter library it execs, and the missing-library behaviour: [Capability adapters](capability-adapters.md#installing-a-binding) and [ADR 0011](adr/0011-bind-adapters-through-a-machine-global-library.md).

Before writing anything, in every mode, the bootstrap script checks CDD's required tools and refuses (exit 4) naming any that is missing (process doc §2.18; mechanics in [Shell helpers](shell-helpers.md#required-tools)). The rendered tree carries `scripts/install-deps.sh`, whose project block the script leaves empty: `/cdd-bootstrap` fills it in its overlay and `/cdd-retrofit` fills it in its reconcile, from the bound adapters and the project's toolchain.

The bootstrap script writes a one-line baseline marker, `.claude/cdd-baseline` (the CDD repo commit the template was rendered from), into every bootstrapped or staged tree; upgrade mode uses it as the three-way merge base for distinguishing template evolution from local customization.

Retrofit classifies every proposed write before it writes anything: clean, mechanical changes go into one batch the user approves once, the rest are asked per file ([ADR 0016](adr/0016-batch-clean-retrofit-changes.md)). Two answers come before classification, because they decide what is rendered and compared: the capability bindings, passed to the current render as flags, and the template renames, which say which path a file is compared on. A file both the project and the template changed is merged with `git merge-file -p <target> <old> <current>`, which prints the result to stdout rather than overwriting the target and exits 0 when conflict-free, positive with the conflict count otherwise; only a conflict-free result can join the batch. `.claude/settings.json` is merged as JSON instead, by a jq three-way merge in the command: a value one side changed takes that side's, lists merge as sets in the template's order, and a value both sides changed differently fails the merge, which sends the file per file. Every file the template ships is compared. The files bootstrap fills with project content (`CLAUDE.md`, the roadmap, the engineering-practices contract, the project overview) never auto-merge, and are not scanned for upstream candidates, since their content is the project's own by definition. Every other file, including one the template adds later, is compared by default. A file new since the baseline is filled from the target's detected state before it is proposed, because a fill-in skeleton's placeholder defaults make false claims about a mature project (an engineering-practices contract saying no gate exists where the project already runs tests and CI). Whatever a run leaves un-upgraded is listed as behind the template, in the summary and in the retrofit commit's body; a file still carrying placeholders and a declined legacy hit get summary categories of their own, so each reads as an action item rather than a success.

Upgrade mode also carries CDD's per-project migrations, all transitional. A workflow change that lives in the project-owned `CLAUDE.md` rather than in a shipped file (the plan/implement split's Workflow bullets) must ride that file's proposal, or the new commands land with nothing telling anyone to use them. A local edit left in a shipped command is proposed per file for a move onto a `CLAUDE.md` declaration or a `.cdd/extensions/` file ([ADR 0020](adr/0020-extend-commands-through-project-owned-extensions.md)), since an edit kept in place makes the next upgrade a hand-merge again. A legacy-token sweep then covers every tracked file the comparison does not, since anything still naming a pre-migration path or command now dangles — a project-local worktree helper under `tools/` most of all; its token table is the only way a renamed path or command reaches files the comparison does not cover. The sweep runs in upgrade mode only (an install target carries no CDD-era tokens); its patterns stay narrow, because a wider one matches stylesheet paths like bootstrap.min.css and bare PROJECT is an ordinary English word; and it reports every hit, acted on or not, as a misclassification is recoverable only while visible.

Upgrade mode has no fallback without a usable marker. A missing one, the `unknown` the script writes when run from a non-git copy of CDD, or a hash the CDD checkout lacks stops the run before the worktree is created, with how to fix it.

`/cdd-retrofit` isolates its writes from the target's current checkout: before rendering, it creates a dedicated `cdd-retrofit` branch and a sibling worktree off the target's HEAD, writes everything there, and makes a single commit on the branch for the user to review and merge via PR. This is the one place CDD runs history-mutating git inside a target, and it is scoped to the dedicated branch only — never the target's existing branches. On the happy path it never touches the current checkout. When the target is not a git repo, the command warns and falls back to writing in place without committing; when it is a git repo with no commits yet (an unborn HEAD, where a worktree can't be created), it falls back to a plain branch in the existing checkout and commits there. Because the worktree branches from HEAD, uncommitted local edits to CDD-managed files are invisible to the upgrade comparison; the command warns when it detects them rather than hard-stopping on a dirty tree.

After the commit, the command leaves the branch a **task record** in the target, so the downstream sessions (`/cdd-pre-pr`, `cdd-worktree-resume`, `cdd-worktree-done`, `cdd-worktree-gc`) treat it as a task already built. It writes a minimal handoff — mode and every applied change as its requirements, no implementation prompt — under `~/.cdd/handoffs/<target repo>/`, then runs `cdd-state seed --base <branch the worktree was cut from>` and `cdd-state set implementation_done` from inside the worktree, with the session id blanked and no lane marker — the retrofit took no lane, so a resume sends the branch to the review-side commands; the mechanics are in [`shell-helpers.md`](shell-helpers.md). The branch-name collision rule also treats a leftover handoff or record under the candidate name as taken. Every fallback path, and a missing or too-old `cdd-state`, skips the record with one line. The post-merge cleanup it recommends is `cdd-worktree-done` from the retrofit worktree, which also deletes the merged branch and reaps the record.

In upgrade mode the two identifiers are recovered from the project's own rendered files rather than asked: `<PROJECT_DIR>` from the handoff path in `cdd-next-step.md` (cross-checked against `settings.json`'s handoff permission), `<PROJECT_NAME>` from the `CLAUDE.md` title (cross-checked against the roadmap's). The command states them in one line and asks only when a value is missing or its sources disagree; a recorded `<PROJECT_DIR>` that differs from the target's folder name gets one warning line, since CDD keys the handoff directory on the folder name.
