# 0036: Upgrade binding shims; keep their backend

**Status:** Accepted

## Context

Issue #178: `/cdd-retrofit` never upgrades a project's existing `.cdd/tracker` / `.cdd/code-host`
shims. Downstream shims still carried the pre-#155 "adapter library missing" hint (curl one adapter
file) instead of the current `cdd-worktree.sh update` route, and had to be re-rendered by hand.

Two things kept them behind:

- A shim's text is generated by `write_binding` in `tools/bootstrap-cdd-project.sh`, not stored
  under `template/`. `write_binding` skips an existing file, and retrofit proposed bindings only for
  capabilities the project did not bind (ADR 0011 decision 4: "never overwriting an existing
  binding"), so a shim was never compared at all.
- Passing the binding flags to both of upgrade mode's renders, the issue's first suggestion, does
  not help: the old render runs the *current* script with `--template-dir`, so both renders emit
  the same shim and the three-way comparison sees no template change.

A shim mixes two owners: its backend and coordinates (Jira site and key, GitLab instance and
project) are the project's choice; the rest of its text is CDD's.

## Decision

1. **An existing binding is CDD-managed for its text and project-owned for its backend and
   coordinates.** Upgrade mode compares it; the backend never changes without the user naming a
   new one.
2. **Recovery by parsing, beside the writer.** `bootstrap-cdd-project.sh --recover-bindings <dir>`
   reads each shim's `lib=` line (the backend it execs, which must be a shipped adapter) and its
   `export` line (the coordinates, checked against the same shapes the flags are validated with)
   and prints the flags that render it again. It writes nothing. A shim it cannot read back — a
   project adapter, a hand-mangled shim, or two GitLab shims naming different projects (one set of
   GitLab flags serves both) — gets a stderr note and is left out. `write_binding` stays the only
   writer; `--recover-bindings` is the only reader, so the two change together.
3. **The old shim is rendered by the baseline commit's own script**, extracted with the old
   template (`git archive <baseline> template tools`), with the recovered flags. The old template
   render itself still runs the current script. If the old script fails — a baseline predating the
   binding flags (#117), or one not knowing a recovered backend — there is no old shim.
4. **Classification.** Target equal to the current render: skip silently. Target equal to the old
   render and the current render different: batch `upgrade`. Everything else — hand-edited, no old
   shim, unrecoverable, or a backend that differs from what the retrofit's detection proposes — goes
   per file, never auto-merged. Shims skip the backend-swap and extension-point verdicts and the
   upstream assessment.
5. **Proposing a new binding still never overwrites an existing one.** Install mode and
   `/cdd-bootstrap` are unchanged. This partially supersedes ADR 0011 decision 4.

## Rejected alternatives

- **Recover through `describe`.** Needs the adapter library installed on the retrofit machine, and
  the coordinates it reports are display strings (`ABC @ acme.atlassian.net`), not the exact
  `JIRA_BASE_URL` / `GITLAB_URL` (scheme and sub-path lost).
- **Pass the flags to both renders.** Both run the current script, so they emit the same shim.
- **Stamp a version in the shim.** Existing shims carry none, so it cannot help the projects that
  motivated #178; versioning is deferred design (process doc §6).
- **Two-way compare, target against current, with no base.** Cannot tell a hand edit from an
  outdated shim.
- **Render the whole old tree with the old script.** Old scripts lack later fixes (the BSD-sed
  substitution, for one); the old render uses the current script for exactly that reason. Only the
  shim needs the old script.

## Consequences

- A later change to the shim's text reaches every bound project on its next upgrade, as an untouched
  file's `upgrade` in the batch.
- A baseline predating the binding flags, or a shim the script did not write, is asked per file.
- The `adapter-bindings` gate covers recovery: an outdated Jira and GitLab shim read back exactly,
  reproduced by a baseline script and refreshed by the current one; a project adapter and
  disagreeing GitLab shims left out.
- A change to the shim's `lib=` or `export` lines must update `--recover-bindings` in the same
  change.
